ADMIN API ENDPOINT REFERENCE
Version: 1.0
Source of truth: current backend implementation in `/api/admin`

===============================================================================
GENERAL CONVENTIONS
===============================================================================

Authentication
- Protected admin routes require: `Authorization: Bearer <admin-jwt>`
- Admin JWTs are issued by `POST /api/admin/auth/login`
- `401` means missing, invalid, or expired token
- `403` means authenticated but not allowed as admin

Common success envelope
```json
{
  "success": true,
  "message": "Optional message",
  "data": {}
}
```

Common error envelope
```json
{
  "message": "Readable error message"
}
```

Notes
- Validation and duplicate-key failures are normalized to `400` by the backend error handler.
- `409` is not currently emitted by the backend, but the frontend may treat conflict-style failures as validation errors.
- Image upload endpoints use `multipart/form-data` with `upload.single(...)`.
- List responses generally use `items` plus `pagination`, and some include `summary`.

AUTH MODULE
===============================================================================

1) Admin Login
- Method: `POST`
- Route: `/api/admin/auth/login`
- Purpose: Authenticate an admin and return a JWT.
- Authentication: Public
- Headers:
  - `Content-Type: application/json`
- Query params: None
- URL params: None
- Request body:
  - `email` string, required, valid email
  - `password` string, required
- Sample request:
```json
{
  "email": "admin@example.com",
  "password": "password"
}
```
- Success response `200`:
```json
{
  "success": true,
  "token": "jwt-token",
  "admin": {
    "id": "66b2f1f4c7c4d13c2f9d1111",
    "firstName": "Amna",
    "lastName": "Malik",
    "email": "admin@example.com",
    "role": "admin",
    "avatar": "https://..."
  }
}
```
- Errors:
  - `400`: missing required fields
  - `401`: invalid credentials
  - `403`: user exists but is not admin
  - `500`: unexpected server error
- Notes:
  - This is the first call in the admin flow.
  - The returned token must be reused for all protected admin endpoints.

13) Create Event
- Method: `POST`
- Route: `/api/admin/events`
- Purpose: Create an admin-managed event record.
- Authentication: Admin JWT
- Headers:
  - `Authorization: Bearer <token>`
  - `Content-Type: application/json`
- Request body:
  - `name` string, required
  - `category` string, required
  - `venue` string, required
  - `date` string/date, required
  - `status` string, optional, recommended values: `Upcoming`, `Live`, `Completed`, `Draft`, `Cancelled`
  - `attendees` number, optional, non-negative
  - `revenue` number, optional, non-negative
  - `organizerName` string, optional
  - `organizerEmail` string, optional
  - `vendorId` string, optional
- Sample request:
```json
{
  "name": "Mehta-Kapoor Wedding",
  "category": "Marriage Halls",
  "venue": "The Royal Ballroom",
  "date": "2026-06-22",
  "status": "Upcoming",
  "attendees": 480,
  "revenue": 28400
}
```
- Success response `201`:
```json
{
  "success": true,
  "message": "Event created successfully",
  "event": {
    "id": "EVT-1042",
    "name": "Mehta-Kapoor Wedding",
    "category": "Marriage Halls",
    "date": "2026-06-22",
    "venue": "The Royal Ballroom",
    "status": "Upcoming",
    "attendees": 480,
    "revenue": 28400,
    "organizer": "",
    "createdAt": "2026-06-22T10:15:00.000Z"
  }
}
```
- Errors:
  - `400`: missing required fields or invalid numeric values
  - `401`: missing/invalid token
  - `403`: non-admin token

FRONTEND INTEGRATION GUIDE
===============================================================================

1) Recommended API call sequence
- Login page:
  - Call `POST /api/admin/auth/login`
  - Store JWT securely in client state/storage
  - Immediately call `GET /api/admin/auth/me` to hydrate the admin session
- App bootstrap after login:
  - Call `GET /api/admin/dashboard/summary`
  - Call `GET /api/admin/dashboard/revenue-analytics`
  - Call `GET /api/admin/dashboard/booking-analytics`
  - Call `GET /api/admin/dashboard/event-status`
  - Call `GET /api/admin/dashboard/vendor-performance`
  - Call `GET /api/admin/dashboard/recent-events`
  - Call `GET /api/admin/dashboard/activities`
- Navigation pages:
  - Load list endpoint first
  - Open detail endpoint when row/card is selected
  - Use create/update/delete endpoints from form/modal actions
  - Refresh list after mutations

2) Page-to-endpoint mapping
- Admin login page:
  - `POST /api/admin/auth/login`
- Admin shell/layout session check:
  - `GET /api/admin/auth/me`
- Dashboard overview:
  - `GET /api/admin/dashboard/summary`
  - `GET /api/admin/dashboard/revenue-analytics`
  - `GET /api/admin/dashboard/booking-analytics`
  - `GET /api/admin/dashboard/event-status`
  - `GET /api/admin/dashboard/vendor-performance`
  - `GET /api/admin/dashboard/recent-events`
  - `GET /api/admin/dashboard/activities`
- Events page:
  - List: `GET /api/admin/events`
  - Detail modal: `GET /api/admin/events/:id`
  - Create form: `POST /api/admin/events`
  - Edit form: `PATCH /api/admin/events/:id`
  - Delete action: `DELETE /api/admin/events/:id`
- Service Categories page:
  - List: `GET /api/admin/event-categories`
  - Detail modal: `GET /api/admin/event-categories/:id`
  - Create modal: `POST /api/admin/event-categories`
  - Edit modal: `PATCH /api/admin/event-categories/:id`
  - Delete modal: `DELETE /api/admin/event-categories/:id`
- Vendors page:
  - List: `GET /api/admin/vendors`
  - Detail modal: `GET /api/admin/vendors/:id`
  - Create modal: `POST /api/admin/vendors`
  - Edit modal: `PATCH /api/admin/vendors/:id`
  - Delete action: `DELETE /api/admin/vendors/:id`
- Bookings page:
  - List: `GET /api/admin/bookings`
  - Detail modal: `GET /api/admin/bookings/:id`
  - Create modal: `POST /api/admin/bookings`
- Users page:
  - List: `GET /api/admin/users`
  - Detail modal: `GET /api/admin/users/:id`
- Calendar page:
  - Month/week/day grid: `GET /api/admin/calendar`
  - Event markers for grid: `GET /api/admin/calendar/events`
- Blog list/editor pages:
  - List: `GET /api/admin/blogs`
  - Detail page: `GET /api/admin/blogs/:id`
  - Create form: `POST /api/admin/blogs`
  - Edit form: `PATCH /api/admin/blogs/:id`
  - Delete modal: `DELETE /api/admin/blogs/:id`
- Notifications widget:
  - List: `GET /api/admin/notifications`
  - Mark read: `PATCH /api/admin/notifications/:id/read`
- Messages widget:
  - List: `GET /api/admin/messages`
  - Mark read: `PATCH /api/admin/messages/:id/read`
- Settings page:
  - Load: `GET /api/admin/settings`
  - Save: `PATCH /api/admin/settings`
- Admin profile page:
  - Load: `GET /api/admin/profile`
  - Save: `PATCH /api/admin/profile`
  - Preferences: `PATCH /api/admin/profile/preferences`

3) Which endpoints feed which UI pieces
- Dashboard KPI cards:
  - `GET /api/admin/dashboard/summary`
- Dashboard revenue chart:
  - `GET /api/admin/dashboard/revenue-analytics`
- Dashboard booking chart:
  - `GET /api/admin/dashboard/booking-analytics`
- Dashboard event distribution chart:
  - `GET /api/admin/dashboard/event-status`
- Dashboard vendor ranking chart:
  - `GET /api/admin/dashboard/vendor-performance`
- Dashboard recent events table:
  - `GET /api/admin/dashboard/recent-events`
- Dashboard activity feed:
  - `GET /api/admin/dashboard/activities`
- Events table cards/rows:
  - `GET /api/admin/events`
- Category table/cards:
  - `GET /api/admin/event-categories`
- Vendor table/cards:
  - `GET /api/admin/vendors`
- Booking table/cards:
  - `GET /api/admin/bookings`
- User table/cards:
  - `GET /api/admin/users`
- Calendar grid:
  - `GET /api/admin/calendar`
  - `GET /api/admin/calendar/events`
- Blog cards:
  - `GET /api/admin/blogs`
- Topbar notifications/messages:
  - `GET /api/admin/notifications`
  - `GET /api/admin/messages`
- Settings cards and chips:
  - `GET /api/admin/settings`
- Profile panel:
  - `GET /api/admin/profile`

4) Dropdown and filter sources
- Category dropdowns:
  - Use `GET /api/admin/event-categories`
- Vendor category filters:
  - Use `GET /api/admin/event-categories` if the UI wants the canonical category list
- Event status filters:
  - Use the UI enum `Upcoming`, `Live`, `Completed`, `Draft`, `Cancelled`
- Vendor status filters:
  - Use `Approved`, `Pending`, `Rejected`, `Suspended`
- Booking payment status filters:
  - Use `Paid`, `Pending`, `Cancelled`
- Blog status filters:
  - Use `Draft`, `Published`
- Settings role chips:
  - Hardcoded by backend response: `Super Admin`, `Admin`, `Vendor`, `User`, `Viewer`

5) CRUD and special action mapping
- Create:
  - Events, categories, vendors, bookings, blogs
- Read:
  - All list and detail endpoints
- Update:
  - Events, categories, vendors, blogs, settings, profile, preferences
- Delete:
  - Events, categories, vendors, blogs
- Status changes:
  - Events: via `PATCH /api/admin/events/:id`
  - Categories: via `PATCH /api/admin/event-categories/:id`
  - Vendors: via `PATCH /api/admin/vendors/:id`
  - Blog publish/draft: via `PATCH /api/admin/blogs/:id`
  - Read flags: notifications/messages read endpoints
- File uploads:
  - Category image: `POST/PATCH /api/admin/event-categories`
  - Blog feature image: `POST/PATCH /api/admin/blogs`
  - Profile avatar: `PATCH /api/admin/profile`

6) Authentication and headers
- Every protected admin request must include:
  - `Authorization: Bearer <admin-jwt>`
- Use `Content-Type: application/json` for JSON requests.
- Use `multipart/form-data` for upload requests.
- Do not send the token to public `POST /api/admin/auth/login`.

7) Expected response patterns
- List endpoints:
  - `data.items`
  - `data.pagination`
  - optional `data.summary`
- Detail endpoints:
  - `event`, `category`, `vendor`, `booking`, `blog`, or `user`
- Mutation endpoints:
  - `success`
  - `message`
  - updated record in `event`, `category`, `vendor`, `booking`, `blog`, `admin`, or `data`

8) Frontend error-handling guidelines
- `401`:
  - Clear token and redirect to login
  - Show “session expired” or “login required”
- `403`:
  - Show “access denied” or “admin access required”
- `404`:
  - Show empty/detail-not-found state
- `400`:
  - Display validation message returned by backend
  - Highlight missing/invalid form fields
- `500`:
  - Show generic server error toast and retry option
- Duplicate/conflict cases:
  - Backend currently normalizes them to `400`
  - Treat as form conflict/validation error in the UI

9) Dependency notes
- Login must succeed before all other admin calls.
- Dashboard widgets can be loaded independently after login.
- Category and vendor create/edit forms can use the category list endpoint for dropdowns.
- Event and booking forms may reference each other through `eventId` and `event`.
- Blog create/update forms need image upload support or an image URL fallback.
- Notifications/messages read actions should refresh the feed after success.

10) Recommended frontend loading order
- Login
- Session validation
- Dashboard summary and charts
- Sidebar/layout data
- Current page list endpoint
- Detail endpoint on demand
- Mutation endpoints from forms/modals
- Refresh current list after mutation
